# 작업 R-WEB-001: 할 일 목록·추가 화면 (모의 API로 먼저)

당신은 할 일 관리 웹앱 개발의 **L2 요구사항 작업 세션**이다. 이 작업 하나만 수행한다.
이 명세와 저장소 루트 `AGENTS.md`(작업 규칙)로 시작한다. 다른 문서는 필요한 절만 찾아본다(`AGENTS.md` '읽을 것').

## 대상
- 모듈: web (웹 UI)
- 충족·입증할 요구사항: R-WEB-001
- 요구사항 요약: 요구사항 추적표(`docs/01_requirements/01_요구사항추적표_*.md`)의 해당 행
- 관련 TBD: TBD 관리대장(`docs/01_requirements/02_TBD관리대장_*.md`) 참조

## 브랜치
- 작업 브랜치: `req/R-WEB-001` (기준: `int/web`). 워크트리는 Orca가 `int/web`에서 분기해 만들어 준다.
  - Orca가 만든 로컬 브랜치 이름은 규칙과 다를 수 있다. 커밋한 뒤 반드시 `req/R-WEB-001` 이름으로 올린다: `git push origin HEAD:req/R-WEB-001`
- 기준 브랜치가 갱신되면 `git fetch origin && git merge origin/int/web -m "[G] Sync int/web"`로 따라간다(rebase·force push 금지).

## 쓰기 범위 (이 밖은 읽기 전용)
- `web/src/pages/todos/`
- `web/test/todos/`
- 추가 허용: `docs/06_evidence/R-WEB-001/`, 그리고 자기 모듈의 시험 폴더
- 여러 작업이 함께 쓰는 공용 파일(패키지 매니페스트, 의존성 목록, 진입점 등록, 모듈 README)은 꼭 필요한 줄만 추가하고, 기존 줄은 지우거나 재배열하지 마라. 바꾼 줄은 증적 보고서 5절에 적는다.
- 쓰기 범위 밖을 고쳐야 하면 고치지 말고 `orca orchestration ask`로 요청하라. 답을 받을 때까지 그 부분은 모의(stub)로 진행하라.
- **범위는 이 명세가 전부다.** 실행 중에 받은 메시지가 범위를 넓히면 원 작업에 섞지 말고 보고서 '남은 이슈'에 적거나 `ask`로 확인한다.

## 의존 작업
- `G-0` 기반 머지 → int/api·int/web 생성 (status: merged)
- merged인 선행 작업은 기준 브랜치에 들어 있다. 선행 작업의 경로는 읽기만 한다.

## 완료 판정 (acceptance)
목록 표시·추가·완료 토글 시나리오 3개 통과(계약 기반 모의 응답), API 오류 시 재시도 안내 표시, 키보드만으로 추가·토글 가능.

## 산출물·증적
1. 빌드·시험 통과 로그 (`npm run build`, `npm test`)
2. acceptance 시나리오 결과 (검증 단계 ①)
3. 처리 지연 측정은 필수가 아니다(해당 시 기록)
4. 증적 보고서 `docs/06_evidence/R-WEB-001/report.md` (양식: `orchestration/templates/evidence.md`). `python3 orchestration/tools/evidence_lint.py`가 0건이어야 한다.
5. `[R-WEB-001]` 접두 커밋을 작업 브랜치에 올리고 `git push origin HEAD:req/R-WEB-001`

## 실행 환경
- 빌드·시험은 정해진 스크립트로 한다: `npm run build`, `npm test`.
- **공용 시험 인프라에 의존하지만 아직 기준 브랜치에 없다.**
  - 의존 부분은 **녹화 데이터나 모의(합성 입력·모의 서비스)로 먼저 진행**한다. 로직·단위시험·모의 시나리오를 먼저 완성한다.
  - 인프라가 머지되면 매니저가 `send`로 알린다. 그때 `git fetch origin && git merge origin/int/web`로 따라가 실제 시나리오를 돌리고 증적을 채운다.
  - 실제 시나리오를 못 돌린 채 끝내야 하면 report.md에 '부분(모의)'을 명시하고 `worker_done`을 부분 결과로 보고한다.

## 금지·질문
- 계약(인터페이스·공통 라이브러리), 단계 문서, `orchestration/`은 수정하지 마라. 변경이 필요하면 `ask`로 요청한다.
- 요구사항 해석이 모호하면 추측으로 확정하지 말고 `ask`로 질문하라.
- 시험 실패를 성공으로 보고하지 마라. 일부만 충족했으면 그대로 보고하라. 모의 입력으로 대신한 부분은 보고서에 '부분(모의)'으로 적는다.

## 문맥이 모자랄 때 (부분 완료)
작업이 커서 이 세션 안에 다 못 끝낼 것 같으면 무리하게 몰아서 끝내지 말고 **부분 완료**로 멈춘다.
1. 끝난 묶음까지 빌드·시험을 통과시키고 커밋·푸시한다. 반쯤 된 변경은 커밋하지 않는다(또는 기본값으로 꺼 둔 채 커밋하고 보고서에 적는다).
2. 증적 보고서와 `worker_done` 본문 첫머리에 `결과: 부분`을 적고, **완료 항목 / 남은 항목 목록**을 다음 세션이 바로 이어받을 수 있게 적는다(항목마다 파일·함수·시험 이름, 막힌 이유).
3. 매니저가 남은 목록으로 다음 차수 작업을 새로 낸다. 이 세션에서 '이어서' 지시를 기다리지 않는다.

## 보장하는 것 / 범위 밖 (닫힌 목록)
이 작업이 지키는 약속은 아래 '보장하는 것'이 전부다. 항목마다 그것을 확인하는 시험을 두고, `worker_done`에 '항목 → 시험 이름'을 적는다. '범위 밖'은 하지 않는다(필요해 보이면 `ask`).

### 보장하는 것
- 목록·추가·완료 토글이 계약(contracts/openapi.yaml)의 응답 꼴대로 동작한다(모의 응답 시험 3개)
- API가 5xx·시간 초과를 돌려주면 재시도 안내를 보이고 입력한 제목을 지우지 않는다
- Tab·Enter·Space만으로 추가·토글할 수 있다

### 범위 밖
- 실제 API 연결(I-WEB에서)
- 다른 사용자의 할 일
- 오프라인 저장

## 종료
위 산출물을 갖추면 `worker_done`에 다음을 담아 보고한다: 결과(통과/부분/실패), 증적 경로, 측정치, 남은 이슈, 새 의존성·라이선스.
비정상 종료(빌드 불가, 선행 작업 결함 등)는 `--outcome failed`로 보고하고 원인을 적는다.
