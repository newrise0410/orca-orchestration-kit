## 4. v0.3 반영 (효율 검토, 2026-11-12)

키트 검토(설치본 dry-run, 현재 Orca CLI 1.4 대조, 두 번째 실사용 프로젝트 읽기 전용 조사)에서 나온 결함과 효율 개선이다. 교훈은 `LESSONS.md` L-14 ~ L-19. 아래 '후보 n'은 5장 번호다.

### 4.1 결함 수정
| 결함 | 원인 | 수정 |
|---|---|---|
| `upgrade --apply`가 '키트 밖 파일과 겹침'을 덮어씀 | 충돌만 `.kit-new`로 보냈다 | 키트 밖 파일·충돌·seed는 모두 `.kit-new`. 덮어쓰기는 `--overwrite-conflicts`만 |
| `status`의 진행 워커 수 오판(끝난 워커를 진행으로 셈), 100개에서 잘림, 이름 대신 dispatch ID | 끝난 상태를 `succeeded`·`failed`로만 봤다. 페이지를 안 넘겼다 | `kitlib.SETTLED_WORKER_STATES`(abandoned·stopped 포함), `nextCursor` 페이지 순회, Orca 작업 제목 → 키트 ID 대응. `cleanup_worker.sh`도 같은 집합 |
| `launch.sh`가 선행·status를 안 보고 투입, W0에서 투입 가능 목록이 빔, `int/common` 생성 안내 없음 | 투입 가능 판정이 L2 전용이었다 | `launch.py`: status todo/ready·hold·게이트·선행 merged(L1은 L2 선행 제외)·기준 브랜치 존재를 확인(`--force`로 끔). 투입 가능 목록은 모든 계층. 없는 브랜치는 만드는 명령을 알려 준다 |
| `bootstrap` 기본값 `all`이 매니저 기동 보고 전에 abandon | 단계 사이에 기다림이 필요한데 한 번에 돌았다 | `--step` 필수, `all` 삭제. abandon은 `--work-run` 필요 |
| 매니저 기동이 Orca에 거부될 수 있음 | 기존 워크트리(`path:`)에 생성 전용 플래그 `--display-name`을 줬다(Orca: 생성 플래그는 새 워크트리에만) | 뺐다. `launch.py`도 기존 워크트리 재사용 때는 `--name`·`--base-branch`·`--repo`·`--display-name`을 넣지 않는다 |
| `sync_main.sh`가 현재 체크아웃의 브랜치를 바꾸고 원격에 자동 push | 체크아웃 전환 방식 | 임시 워크트리에서 머지하고 로컬 브랜치만 옮긴다(체크아웃된 브랜치는 깨끗할 때만 ff). 원격은 `--push`일 때만 |

### 4.2 효율 개선

## 6. v0.4 반영: 모델 자동 라우팅 (2026-11-16)

**요청:** 작업 난이도·속도에 맞는 모델과 effort를 자동으로 고르고, Claude 말고도 구독제 CLI(Codex OAuth, Antigravity `agy`, Grok CLI)를 Orca처럼 섞어 쓴다. 핵심은 '모델에 최적화된 자동 라우팅'.

**실행 계층은 Orca가 이미 갖고 있다.** Orca 1.4의 `worker-start --agent <claude|codex|antigravity|grok …> --model <id> --effort <수준>`가 구독 CLI를 워크트리별로 띄운다(Conductor가 하는 일). OpenCode식 API 관문은 쓰지 않는다. 키트가 더하는 것은 **작업마다 무엇으로 띄울지 정하는 결정 계층**이다.

### 6.2 결정 방법 (LLM을 부르지 않는다)
1. **분류:** 기본 난이도 2에서 L1·체계 통합(4), 계약 작업(제목에 계약 말이 있거나 `contracts/`를 씀, +1) 또는 그 밖의 공통 기반 F-*(+0.5), 쓰기 범위 넓이(6곳 +0.5, 12곳 +1), 최상위 폴더 3개 이상(+0.5), 완료 조건 수(6개 +0.5, 12개 +1), 어려운 말(동시성·보안·마이그레이션 등 0.5씩 최대 +1. **프로젝트 작업의 30%보다 많이 나오는 말은 그 분야의 일상어로 보고 뺀다**), 제목의 쉬운 말(−1, 어려운 말이 없을 때), 성능 측정(+0.5), 선행 4개 이상(+0.5), 앞선 시도 실패(+1씩, 최대 +2). 작업 항목 `difficulty`가 있으면 그것을 쓴다. 태그(design·contract·frontend·test·docs·refactor·debug·config·research·coding·integration·review)는 제목·완료 조건·쓰기 범위에서 뽑는다. 뒤에 기대는 미완료 작업이 5개 이상이면 임계 경로(품질 여유 +0.5, 속도 가중 +0.3).
   - 보정: 실사용 프로젝트 작업 74개로 돌려 맞췄다. 첫 판은 '계약'·'권한'·'성능'처럼 그 분야에 늘 나오는 말과 긴 완료 조건 때문에 난이도 4~5가 80%, Opus가 39건이었다. 빈도 거르기·문턱 조정 뒤 난이도 분포 2:11 · 3:36 · 4:17 · 5:10(`docs/VERIFY.md` 9장).
2. **점수:** `−under×max(0, 난이도−quality) − cost가중×cost − speed가중×(5−speed) + head×min(1, quality−난이도) + 강점(태그당 0.75, 최대 1.5) + 실적 + prefer(+2)` − 진행 중 워커(0.4씩) − 하루 사용량 기준 초과 − 이 작업에서 실패한 모델(2.5) − 교차 검토 위반(3). 목표별 가중은 `routing.py OBJECTIVES`. 구독제라 cost는 돈이 아니라 한도 소모이고, 다시 띄우고 검토하는 비용이 더 크므로 balanced는 품질 여유(head 1.0)를 소모(0.4)보다 무겁게 둔다. 결과적으로 **난이도를 여유 있게 넘는 모델 가운데 싼 쪽**이 이기고, 실패·부하·한도가 쌓이면 다른 구독으로 넘어간다.
3. **제외:** `routing.agents` 밖, CLI 없음, CLI 모델 목록에 없는 모델(Claude는 별칭이라 목록 확인 없이 믿는다), 쿨다운, 최저 품질 미달, 동시 상한(모두 차면 상한 무시).
4. **effort:** 난이도 1~2 low, 3 medium, 4 high, 5 xhigh. 목표 quality면 한 단계 위, economy·speed면 아래. 모델이 난이도보다 2 이상 강하면 한 단계 아래. 임계 경로는 난이도 +0.5로 본다(강한 모델이라고 effort를 낮추지 않게). `max`는 명시할 때만. Antigravity Gemini처럼 추론 수준이 모델 ID에 든 모델은 ID 변형을 고른다.
5. **학습:** 구현 투입마다 결과 점수를 매긴다. merged인데 뒤에 retry가 없으면 1, retry가 있으면 0.6, 다시 띄운 앞 시도와 todo로 되돌아온 시도는 0, retry 마지막은 1. 검토 판정(`models.py feedback`: pass 1 · minor 0.7 · major 0.3 · fail 0)이 있으면 그 점수로 덮는다. (모델, 난이도 대역)별 평균을 사전값 0.67로 평활해 `4×(평균−0.67)`을 더한다.

### 6.3 판단과 한계
- **결정적 점수 + 학습 보정을 택했다.** 투입마다 LLM으로 분류하면 느리고 비싸며 재현되지 않는다. 매니저는 분류가 틀린 작업에만 `difficulty`를 적는다. 판단이 필요한 몫은 매니저(LLM)가 tasks.yaml을 쓸 때 이미 들어간다.
- **카탈로그 점수는 작성 시점의 추정이다**(2026-11 기준 Claude fable/opus/sonnet/haiku 별칭, Codex gpt-6-astra·gpt-6.1-sol·gpt-6.1-terra·gpt-6-luna, Antigravity gemini-4-neon·gemini-4-carbon·claude-opus-5-5, Grok grok-4.7(effort low~high, build-fast는 뺌)). `discover`가 카탈로그에 없는 새 모델을 알려 주고, 프로젝트는 `models.yaml models:`로 덮어쓴다.
- **탐색(일부러 다른 모델에 맡겨 보기)은 하지 않는다.** 결과가 쌓이는 모델만 학습된다. 비교가 필요하면 `pin`·`prefer`로 잠시 바꾼다.
- **구독 계정 전환은 하지 않는다.** `orca account select`는 호스트 전체 설정이라 동시 투입과 사용자 세션에 번진다. 한도는 구독 단위 쿨다운으로 다룬다. 한도 감지는 사람(매니저)이 워커 보고·화면으로 하고 `cooldown`을 건다(자동 감지는 다음 후보).
- **Orca 사용량 파일**(`~/.config/orca/orca-{claude,codex}-usage.json`)은 Orca 내부 형식이다. 모델·날짜별 출력 토큰 합만 읽고, 형식이 바뀌면 조용히 빈 값으로 둔다. Antigravity·Grok은 집계가 없다.
- **실기동에서 드러난 것(v0.4.1):** Orca에서 꺼진 에이전트는 `worker-start`가 `agent_unconfigured`로 거부한다 → launch가 그 구독을 쿨다운하고 한 번 다시 라우팅한다. snap으로 깐 `agy`는 AppArmor 격리 때문에 `$HOME`의 숨김 폴더에 있는 Orca CLI 심을 실행하지 못해 `worker_done`·`ask`를 보낼 수 없다 → discover가 snap 설치본을 표시하고 라우팅에서 뺀다(`agents.<id>.allow_confined`로 풀 수 있다). Antigravity는 작업 폴더 신뢰가 필요하고, snap 설치본은 신뢰 목록도 `~/snap/antigravity-cli/common/.gemini/…`에서 읽는다(키트는 신뢰를 대신 주지 않는다).
- **다음 후보:** 워커 화면에서 한도 문구를 찾아 쿨다운을 자동으로 거는 것(status.py), 작업 소요 시간(투입 → merged) 학습, 대시보드 모델 배분 탭.

- **복사 버튼:** `file://`로 열면 클립보드 API가 막히므로 textarea 복사로 대신하고, 그것도 안 되면 명령을 대화창에 띄운다.
- **JEV 난이도 판정(선택, 기본 꺼짐):** 규칙 분류기는 낱말 목록이라 프로젝트마다 다시 맞춰야 한다. TypeSafe JEV(글을 쓰지 않고 판정·확률만 내는 모델, 입력 100만 토큰당 수 센트)에 제목·완료 조건을 5단계 점수 질문으로 보내 뜻으로 난이도를 본다. 그러나 작업 내용이 외부로 나가고 결과가 재현되지 않으며 키가 없는 환경도 있으므로 **기본은 꺼 두고**, 켜도 `shadow`로 기록만 한 뒤 `models.py stats`의 비교(JEV가 더 어렵게 본 작업의 결과가 낮은가)를 보고 `live`로 바꾼다. 모델 선택(점수·가용성·쿨다운·실적 학습)은 그대로 규칙이 한다. JEV는 우리 실적을 배우지 못하고 구독 한도도 모르기 때문이다. 작업에 `difficulty`를 직접 줬거나 검토·재시도 투입이면 묻지 않는다. 같은 내용은 `state/jev_cache.json`에서 다시 쓰고, 대시보드는 캐시만 읽어 30초 재빌드가 외부를 부르지 않게 했다.
- **예제:** `make_demo.sh`가 가상 라우팅 상태(모델 캐시·쿨다운·dispatch 한 줄)를 만들고 `KIT_ORCA_HOME`을 빈 폴더로 돌려, 예제 대시보드가 실행한 머신의 CLI·사용량에 따라 달라지지 않게 했다.

## 8. v0.7 반영: 구독 CLI 자동 업데이트·카탈로그 계열 (2026-11-25)

- **왜:** 카탈로그에 모델 ID를 하나씩 적어 두었더니 CLI에 새 판이 나와도 옛 ID를 계속 썼다(Codex gpt-6.2가 있는데 6.1-sol·6-astra). 옛 ID가 목록에서 빠지면 그 항목이 조용히 제외됐다(Antigravity claude-opus-4-6-thinking). `discover`는 ID가 목록에 있는지만 봐서 둘 다 잡지 못했다.
- **계열(`family:`):** 판 번호 자리를 `{v}`로 적고(`gpt-{v}-sol`, `grok-{v}`), effort가 ID에 들어 있으면 `{effort}`도 적는다(`gemini-{v}-neon-{effort}`). `route()`가 discover 결과로 가장 높은 판을 고르고 model_by_effort를 다시 만든다. 판 비교는 숫자 묶음(`6.2` > `6.1` > `6`, `5-5`도 읽는다). 꼴은 앞뒤를 고정해서 `grok-4.7-build-fast` 같은 변형은 계열에 들지 않는다. 목록을 모르면(Claude 별칭·목록 실패) 카탈로그 기본 ID를 쓴다.
- **품질 점수는 따라가지 않는다:** 같은 계열의 새 판은 같은 등급으로 본다. 새 계열(다른 이름)은 점수를 사람이 정해야 하므로 `discover`가 "카탈로그에 없는 모델"로만 알린다. 계열 옛 판은 알림에서 뺐다.
- **프로젝트 고정:** `models.yaml models:`에서 model을 직접 정한 항목은 계열을 끈다(그 판을 쓰겠다는 뜻으로 본다).
- **CLI 업데이트:** 네 CLI 모두 자체 업데이트 명령이 있다(`claude update`, `codex update`, `agy update`, `grok update`). 카탈로그 `agents.*.update`에 적고 `update_clis()`가 돌린 뒤 `--version`으로 앞뒤 판을 남긴다(`state/cli_update.json`). launch.sh는 하루 한 번, 워커를 띄우기 전에 동기로 돌린다(띄우는 중에 실행 파일이 바뀌지 않게). 네 CLI 합쳐 15초 안팎이었다. dry-run·`KIT_NO_CLI_UPDATE`·`auto_update: off`면 하지 않는다.
- **snap 설치본은 건너뛴다:** snap이 관리하고, 워커로도 못 쓴다(orca CLI 실행 불가). Antigravity는 공식 설치본(`~/.local/bin/agy`, 스스로 업데이트)을 쓴다. Snap Store의 antigravity-cli는 공식 배포가 아니라 커뮤니티 포장본이다.

## 9. v0.7 반영: 품질 = 공개 벤치마크, 잔여 한도 (2026-11-25)

- **어떤 벤치마크인가:** 우리 라우팅은 "모델"이 아니라 "CLI 에이전트 × 모델 × effort"를 고른다. Terminal-Bench(tbench.ai) 공식 리더보드가 같은 단위(Claude Code · Opus 5.5 · max)로 해결률과 95% 신뢰구간을 낸다. 모델만 재는 지수(AA 지능 지수, SWE-bench Verified)는 실행 환경 차이를 담지 못한다(같은 Gemini 4 Neon이 범용 시험 환경 12.8%, Antigravity 안에서 39.0%라는 보도). SWE-bench Verified는 포화돼 기록처 한 곳이 새 모델 평가를 멈췄다.
- **받는 방법:** 리더보드 페이지가 품은 데이터(이스케이프된 JSON)를 읽는다. 관리자가 `models.py bench`를 돌릴 때만 받고, 라우팅은 결과 파일만 읽는다(오프라인·재현). 키트 판은 `tools/bench_scores.yaml`, 프로젝트가 직접 받으면 `state/bench_scores.yaml`(더 새 것을 쓴다). 원래 표를 통째로 옮기지 않고 카탈로그에 해당하는 줄만 출처·날짜와 함께 둔다. AA는 무료 Data API(키, 하루 100회, 출처 표기 필수)로만, 키가 있을 때 참고값(지능 지수·출력 속도)으로 남긴다. 사이트를 긁지 않는다.
- **환산:** 품질 = 5 × 해결률 ÷ 카탈로그 안 최고 해결률(최저 1). 처음엔 1 + 4 × 비율로 했더니 해결률 40%인 Haiku가 3.4가 돼 임계 경로의 계약 작업을 맡았다. 비례 환산이면 3.0이고 Sonnet(4.9)이 맡는다. 모델의 가장 좋은 effort 점수를 쓴다(대부분 max).
- **판 맞추기:** 카탈로그 `bench_name: 'GPT-{v} Sol'`과 에이전트 `bench_agent: 'Codex'`로 줄을 찾고, 판은 family로 고른 판을 쓴다. 그 판 점수가 아직 없으면 바로 아래 판 점수를 쓰고 "옛 판"으로 적는다(새 판이 보통 같거나 낫다). 다른 CLI의 같은 모델 점수는 빌리지 않는다(Antigravity의 claude-opus는 Claude Code 점수가 있어도 "벤치 없음").
- **벤치에서 바꾸지 않은 것:** 속도(평균 소요 시간에 이상치가 있다: Terra 2.1분, Haiku 2.3분인데 출력 토큰 386k), 소모(구독마다 한도 단위가 달라 출력 토큰을 구독끼리 비교할 수 없다). 둘 다 참고값으로만 남겼다. 강점 태그도 아직 사람이 정한다.
- **벤치가 바꾼 판단:** Gemini 4 Carbon(64.5%)이 Neon(61.2%)보다 높아 카탈로그의 "Carbon은 가벼운 쪽" 추정이 틀렸다(cost 2.5, speed 3으로 고침). Grok 4.7은 38.8%로 추정(4)보다 낮다(2.9). Codex GPT-6.1 Terra는 53.3%로 추정(3)보다 높다(4.1).
- **effort 곡선(참고):** 같은 모델의 effort별 점수가 있는 세 모델(GPT-6 Astra, Fable 5.1, Opus 5)에서 high와 max의 차이는 1~3%p, medium은 4~8%p, low는 9~18%p 낮았다. 출력 토큰은 max가 high의 1.5~2배다. pick_effort가 xhigh·max를 드물게 쓰는 근거로 둔다.
- **잔여 한도:** Orca가 구독마다 사용률을 모은다(`orca account list --json` → `rateLimits`: 창마다 usedPercent·windowMinutes·resetsAt). Claude는 Fable 주간을 따로, Antigravity는 모델 묶음(Gemini / Claude and GPT)별로 센다. 키트는 숫자만 5분 캐시한다(계정 이메일 등은 남기지 않는다). 창 하나라도 98% 이상이면 초기화까지 제외한다(자동 쿨다운). 수동 쿨다운이나 하루 토큰 기준(`daily_soft_tokens`)과 달리 실제 한도를 본다. 주간 창은 절대 사용률이 아니라 지난 기간 비율과 비교한다(월요일에 38%면 빠르고, 금요일에 70%면 괜찮다). 쓸 수 있는 구독이 모두 소진이면 기본 에이전트로 밀어 넣지 않고 launch.sh가 보류한다.
- **동점 규칙:** 실제 작업은 난이도 2~3에 몰리는데 동점도 거기 몰렸다(balanced d=3 coding 3자 동점). 전에는 카탈로그 순서와 부동소수 오차(0.35000000000000001 > 0.35)가 갈랐다. 이제 점수를 소수 6자리로 맞춘 뒤 부하 적은 구독 → 이 대역 실적 → 소모 적은 쪽 → 품질 → 키 이름 순으로 가리고, 동점이었으면 근거에 적는다.
- **실적 대역:** 임계 경로 작업은 점수 계산에 난이도 +0.5를 쓰는데 실적 조회도 그 값으로 해서, dispatch.tsv에 남는 난이도(+0.5 전)와 대역이 어긋났다(3.0 → 기록 mid, 조회 high). 조회를 기록 대역으로 맞췄다.
- **계정 전환은 하지 않는다:** 같은 구독에 다른 계정이 있고 여유가 있으면 제외 이유에 알리기만 한다. Orca 계정 선택은 사람의 다른 세션에도 영향을 주므로 키트가 바꾸지 않는다.

## 10. v0.8 반영: 한도 전환 (2026-11-25)

- **왜:** 잔여 한도(9장)는 새 투입만 막았다. 이미 도는 워커가 한도에 걸리면 매니저가 손으로 했다: 진행분 확인 → 커밋 → 워커 정리 → 쿨다운 → 다시 투입. 손으로 하면 커밋하지 않은 변경을 잃거나, 재투입이 처음부터 다시 하거나, 검토가 구현한 구독으로 가기 쉬웠다.
- **감지:** 정지 점검이 워커의 dispatch 기록(구독·카탈로그 키)으로 그 모델에 걸리는 창(공통 세션·주간, Fable 주간, Antigravity 묶음)을 본다. **100%**일 때만 `한도 정지`다. 새 투입 제외 기준(98%)보다 높게 둔 것은 도는 워커를 멈추는 일이 더 무거워서다. 모델 키가 없는 워커(직접 고른 agent/model)는 공급자 공통 창만 본다.
- **보존:** 워커를 먼저 멈춘 뒤(파일이 바뀌는 중에 찍지 않게) 임시 인덱스(`GIT_INDEX_FILE`)로 작업 트리 전체를 트리로 쓰고 HEAD를 부모로 한 커밋을 `wip/<ID>-quota-<시각>`에 둔다. 작업 브랜치·인덱스·파일은 건드리지 않는다. 이어받는 워커는 같은 워크트리에서 그대로 시작하고, 보존 브랜치는 비교용 안전판이다.
- **이어받기 모드(`handoff`):** 재투입(`retry`, 지적만 고친다)과 뜻이 달라 따로 뒀다. 명세 = 원 명세 + "이어받기" 절(앞 워커·보존 브랜치·기준 이후 커밋·커밋하지 않은 파일, 결과를 다시 확인할 것). 검토 워커는 검토 명세에 같은 절을 붙인다. 앞 명세에 재투입 지적(`### 지적`)이 있었으면 메모로 넘긴다. Orca 제목은 `<ID> handoff-h1`(검토는 `<ID>-RV-h1`).
- **대기 판정:** 곧 풀리는 한도(기본 30분)는 기다리는 편이 싸다(새 워커는 맥락을 다시 읽는다). 다른 구독도 한도면 옮길 곳이 없다. 검토 워커는 구현한 구독(이어받기 앞뒤 모두)이 아닌 후보만 받는다. 남은 후보가 구현 구독뿐이면 독립성을 잃느니 기다린다.
- **대기 뒤 재개:** 한도에 걸린 CLI는 멈춰 있을 뿐 한도가 풀려도 스스로 이어 하지 않는다. 대기로 판정하면 `state/quota_wait.json`에 풀리는 시각을 적고, 그 시각이 지난 뒤 `quota_switch.py`가 돌면 `send --to dispatch:<id>`로 '한도가 풀렸다, 이어서 하라'를 보낸다(멈춘 워커는 턴이 끝난 상태라 바로 받는다). 이미 끝난 워커면 기록만 지운다. 정지 점검은 풀린 대기를 '한도 풀림'으로 알린다. `--due`는 할 일이 있는지만 종료코드로 알려 예약 점검의 사전 확인에 쓴다.
- **깨우는 쪽:** 매니저는 메일이 와야 깨어나므로, 한도가 풀리는 시각이나 자는 동안 생긴 한도 정지는 다른 일로 깨어날 때까지 처리되지 않았다. Orca에는 '이 시각에 메일 보내기'가 없다. 예약 실행(`orca automations`)은 실행마다 에이전트를 띄우고(구독 소모), 한 번만 실행(`--once --by`)은 봇 전용이다. 그래서 예약 실행의 **사전 확인(precheck)**만 쓴다: 사전 확인이 0으로 끝날 때만 에이전트가 뜨므로, `quota_watch.py precheck`는 할 일이 있으면 매니저 Run에 메일(`send --to run:<work_run>`, 매니저를 깨운다)을 보내고 **언제나 1로 끝난다**. 같은 내용은 30분에 한 번만 다시 알린다. 판단과 전환은 깨어난 매니저가 `quota_switch.py`로 한다(예약 실행이 워커를 멈추지 않는다). 사전 확인에 부수 효과를 두는 것은 원래 용도와 다르지만, 에이전트 없이 Orca가 관리하는 주기 실행을 얻는 유일한 길이었다.
- **사전 확인 환경(실측):** 작업 폴더에서 돌고, 셸로 실행되며(`cd … && X=… 명령`이 된다), `ORCA_CLI_COMMAND`가 없고 PATH의 `orca`가 `/usr/bin/orca`(화면 낭독기)였다. 그래서 설치 명령이 Orca CLI·python3 경로를 절대 경로로 박는다.
- **넘겨받을 구독의 여유(v0.8.1, 현장 피드백):** 독립 검토 구독이 codex·agy 둘뿐인 구성에서 전환이 대부분 대기로 끝났고 매니저가 기본값을 wait로 바꿨다. 원인 둘: (1) 넘길 곳을 98% 미만인지만 봐서, 세션 90%인 쪽으로 넘기면 곧 또 멈췄다. (2) 검토 독립성이 점수 감점(−3)이라 구현한 구독이 1순위로 남으면 다른 독립 후보가 있어도 대기했다. 이제 후보마다 남은 양(`switch_min_headroom`, 30%)과 5시간 창의 소모 속도(사용률 ÷ 지난 시간, 창이 30분 넘게 열렸을 때만)를 보고, 앞 워커가 풀릴 때까지(최대 `switch_need_minutes` 120분) 버틸 후보로만 넘긴다. 검토 이어받기는 구현한 구독(이어받기 앞뒤 모두)을 후보에서 아예 뺀다. 고른 구독은 `--agent/--model/--effort`로 launch에 그대로 넘긴다(`kit.yaml review.agent` 고정이 한도 찬 구독을 다시 고르던 결함). 이렇게 하면 넘긴 뒤 또 멈추는 경우가 줄어 기본값 switch를 그대로 둘 수 있다.
- **실적:** 한도는 품질 문제가 아니므로 멈춘 투입(`state/quota_switch.tsv`의 dispatch)은 성공·실패 어느 쪽에도 넣지 않는다. 이어받은 투입은 새 투입처럼 센다(머지되면 그 모델의 성공).
- **하지 않은 것:** 같은 구독의 다른 계정으로 바꾸기(9장과 같은 이유), 화면 문구(usage limit 등)로 감지하기(Orca 한도 수치가 더 확실하다. 화면을 읽을 수 없는 워커도 있다), 원격에 보존 브랜치 올리기(로컬 브랜치다. 워크트리와 같은 저장소라 바로 보인다).
- **커밋 없음 기준(v0.8.3, 현장):** 보완 워커가 앞 차수와 같은 브랜치를 쓰면 마지막 커밋이 앞 차수의 것이라 갓 띄운 워커가 '커밋 없음'으로 잡혔다. 기준 = max(마지막 커밋, 이 투입 시작). 투입 시각은 dispatch.tsv 기록을 쓴다(Orca 워커 기록에는 시작 시각이 없다).
- **필터 중단(v0.8.3, 현장):** codex가 경계 검사를 벗어나는 입력을 찾는 검토에서 안전 필터로 끊겼는데, 한도가 아니라 '한도 정지'로 안 잡혔고 워커는 살아 보였다. Orca 워커 기록(`worker-list`·`worker-show`)에는 중단 사유가 없어서 `worker-read`의 transcript(메시지 = role + blocks)를 읽는다. 오탐을 줄이려고 마지막 assistant 응답 두 개의 글·오류 블록만 보고 도구 결과(읽은 문서·시험 출력)는 보지 않는다. 문구는 CLI별 차단 메시지(이용 정책 위반, flagged/blocked, content filter, finish_reason safety 등)다. 처리는 한도 전환과 같은 절차를 쓰되 기다려도 풀리지 않으니 대기 판정(곧 풀림)이 없고, 같은 모델은 같은 입력에서 또 끊기기 쉬워 그 작업의 후보에서 뺀다(같은 모델의 다른 작업은 그대로: 현장에서도 다른 검토 2건은 정상이었다). 실적에는 넣지 않는다(품질 문제가 아니다).
- **필터 중단은 화면에 있다(v0.8.4, 현장):** codex 안전 필터 안내(`ⓘ This content can’t be shown` / `We take extra care with some cybersecurity requests…`)는 응답 블록으로 기록되지 않아 transcript에는 tool-call·tool-result만 남는다. 화면에 찍히고, Orca가 보내는 escalation 메일(`Worker stopped on an error without reporting`, stopReason=errored)의 "Last output:"에 화면 끝이 담긴다. 그래서 감지 입력을 셋으로 늘렸다: transcript 마지막 응답(부분 일치), 진행 중 워커의 터미널 화면 끝(`worker-read --source terminal` → `result.terminal.tail`, 실측), 메일의 Last output. 끝난 워커는 화면이 해제되므로(archive_unavailable) 메일이 유일한 증거다. 화면·메일에는 검토 대상 문서 글이 섞이므로 안내 블록 고정 줄과 줄 전체가 맞을 때만 잡는다(문장 속 인용은 무시). errored인데 맞는 문구가 없으면 '오류 중단'으로 알리고 자동으로 넘기지 않는다(모르는 오류를 필터로 보고 모델을 빼면 안 된다).

## 11. v0.10 반영: 워크트리 정리 (2026-11-25)
- **왜:** Orca는 워커마다 워크트리를 만들지만 끝난 뒤 치우지 않는다. 키트의 `cleanup_worker.sh`는 워크트리·브랜치·상위 브랜치를 하나씩 손으로 줘야 해서 검토·재투입·이어받기·한도 전환 워크트리가 쌓였다(실사용 저장소 하나에 59개).
- **원칙: 잃을 것이 없을 때만 지운다.** 지운 뒤 되살릴 수 없는 것은 커밋하지 않은 변경, 어디에도 머지되지 않은 커밋, 사람이 쓰는 터미널·채팅이다. 그래서 변경 없음 + HEAD가 기준·메인에 들어 있음 + 진행 중 디스패치 없음 + 1시간 넘게 쉼 + 사용자 고정 아님을 모두 요구한다. 작업 브랜치(`req/<ID>`)·통합 브랜치는 이력이라 지우지 않고, 워크트리가 쓰던 로컬 브랜치만 지운다.
- **주인 찾기:** Orca 워커 기록(작업 Run, 끝난 것 포함)의 workspace → dispatch → 키트 작업. 없으면 dispatch.tsv의 워크트리 이름(launch.sh가 정함), 그다음 브랜치 이름(`req/<ID>`, `req/<ID>-RV…`). 주인을 모르는 워크트리는 사람이 만든 것일 수 있어 자동으로 지우지 않는다(`--orphans`일 때만, HEAD가 메인에 다 있을 때).
- **검토 워크트리:** 검토 보고서 브랜치는 머지하지 않고 보고서 폴더만 가져오므로(procedures/review.md 2) '머지됨'으로 판정할 수 없다. 대신 보고서 폴더가 메인에 들어왔는지(`git cat-file -e <메인>:<폴더>`)를 본다.
- **자동:** launch.sh가 한 시간에 한 번 '정리'만 지운다. 매니저가 깨어나 투입할 때마다 조금씩 치우는 것이 이정표에 몰아서 지우는 것보다 덜 쌓인다. 정지 점검은 지우지 않고 알리기만 한다.

## 12. v0.12 반영: 정해진 전이는 도구가 (LangGraph와 비교, 2026-11-28)
- **비교:** 키트는 LangGraph와 같은 문제를 다른 규모로 푼다. 작업 DAG(`tasks.yaml` deps)는 그래프, `tasks.yaml`·`dispatch.tsv`·git 브랜치는 State, git merge(`req/*` → `int/*` → main)는 병렬 분기 결과를 합치는 reducer, 파일·git에 남는 상태와 한도 전환의 wip 브랜치는 checkpointer, `ask`·결정 게이트·확인 창은 `interrupt()`, `routing.py`는 조건부 엣지, `launch.sh`의 여러 투입은 `Send` 팬아웃, 3계층은 supervisor·subgraph, '같은 계열 2회 → 범위 결정'은 `recursion_limit`에 해당한다.
- **다른 점:** (1) 노드 하나가 LLM 호출 한 번이 아니라 몇 시간짜리 자율 세션이라, 노드 안의 멈춤·필터·한도를 밖에서 감시하는 장치가 키트의 절반이다. (2) 상태를 공유하지 않고 워크트리로 격리한 뒤 git으로 합친다. (3) **엣지가 코드가 아니라 매니저(LLM)의 판단이었다.** 유연하지만 비싸고(현장 매니저 6시간 3,200만 토큰), 가끔 빠뜨린다(할당 누락, 깨어나지 않음).
- **가져온 것:** 엣지 가운데 판단이 필요 없는 것을 코드로 옮겼다(`advance.py`). 구현 통과 → 검토 투입, 검토 차단 → 실적·보완 투입, 같은 계열 연속 → hold. 판단이 필요한 것(병합 관문, 범위 선택지, 부분 완료의 다음 차수, 형식 없는 보고)만 `[판단]`으로 남겨 매니저에게 준다. LangGraph의 '코드로 된 엣지 + interrupt' 구조다.
- **조건:** 결정적 전이는 입력이 구조적이어야 한다. 그래서 worker_done 본문 첫 줄을 고정했다(`결과: 통과|부분|실패`, `판정: 통과|차단 · H n · M n · 계열: …`). 형식이 없으면 도구는 추측하지 않고 `[판단]`으로 넘긴다.
- **이력:** `tasks.yaml`은 현재 상태만 남는다. checkpoint 이력처럼 전이를 `state/events.jsonl`에 덧붙여(dispatch·status·feedback·switch·advance) 되짚기와 지표에 쓴다.
- **LangGraph를 들이지 않은 이유:** 실행 기반(세션·워크트리·메일)은 Orca가 맡고, 필요한 것은 그래프 엔진이 아니라 몇 개의 결정적 전이다. 표준 라이브러리 + PyYAML 원칙을 지킨다.
- **안전장치:** 같은 전이가 두 번 일어나지 않게 처리한 메일 ID를 남기고, 작업이 기대한 상태가 아니거나 그 보고 뒤에 같은 작업의 투입이 또 있거나 오래된(24시간) 메일은 건너뛴다. 도구는 매니저가 부른다(별도 데몬이 아니다): 매니저의 메일 처리와 동시에 같은 작업을 고치지 않게.

## 13. 효과를 재는 법 (2026-11-28)
- **키트 안에서 잴 수 있는 것**(`metrics.py`, 새 기록 없이): 처리 시간, 겹침 배수, 재작업, 복구, 자동 전이, 토큰. 이정표마다 한 번 돌려 `docs/` 지표 문서에 남기면 키트 판 사이의 변화(예: v0.12 advance 뒤 매니저 토큰·[판단] 수)를 본다.
- **겹침 배수는 속도 비교가 아니다.** 작업 기간 합 ÷ 열려 있던 시간은 '한 에이전트가 같은 일을 같은 시간에 한다면'의 상한이다. 실제로 한 세션은 문맥이 커질수록 느려지고 비싸지며(L-23), 반대로 매니저·검토·병합 관문의 오버헤드는 오케스트레이션에만 있다.
- **단일 에이전트 기준선(벤치마크)을 만들려면:** (1) 이미 끝난 작업 가운데 크기가 다른 4~6개(L2 위주, 수용 기준과 시험이 있는 것)를 고른다. (2) 투입 당시의 명세(`orchestration/specs/<ID>.md`를 그 투입 커밋에서)와 기준 브랜치에서 시작한다 — 나중에 고친 명세를 쓰면 기준선이 유리해진다. (3) A: 같은 모델의 한 세션에 명세를 모두 주고 끝까지, B: 키트(워커·검토·병합 관문). 모델·effort·기계를 같게. (4) 잰다: 수용 기준을 모두 통과할 때까지의 벽시계 시간, 토큰(`usage.py`), 사람 개입 수, 병합 관문 전체 시험과 독립 검토가 찾은 결함 수. (5) 표본이 작으니 유의성 대신 원값과 각 판의 실패 사례를 적는다. 한 번 돌리는 데 실제 작업 몇 개 분량의 토큰이 드니 이정표 때만.
- **함정:** 같은 작업을 두 번째로 하는 쪽은 저장소에 이미 답이 있다(브랜치를 기준 커밋에서 새로 만든다). 검토가 잡은 결함 수는 검토가 있는 B에서만 높게 나온다 → 두 판 모두 같은 독립 검토를 끝에 한 번 더 돌려 남은 결함으로 비교한다.
