# 절차: {{MAIN_BRANCH}} 머지 관문 — {{PROJECT_NAME}} (교훈 L-03 ~ L-05, L-08, L-11)

매니저가 `int/*`(또는 `int/common`) → `{{MAIN_BRANCH}}` 머지를 할 때 따른다. 관문을 통과하지 않은 후보는 올리지 않는다.

1. **관문용 체크아웃을 따로 둔다(L-04).** 관문은 메인 체크아웃에서 돌리고, 끝날 때까지 그 체크아웃의 브랜치·파일을 건드리지 않는다. 기다리는 동안 하는 문서 작업은 별도 워크트리에서: `git worktree add ../<저장소>-l0 int/common`. 원격 실행은 단계마다 작업 트리를 동기화하므로 체크아웃을 바꾸면 관문이 다른 트리를 돈다.
2. **머지 범위를 먼저 확인한다(L-08).** 확인은 **실패하면 멈추는** 형태로 쓰고 머지를 `&&` 뒤에 둔다. `;`로 이으면 범위 밖 파일이 출력돼도 머지가 진행된다. 비ASCII 경로는 `core.quotePath=false`가 있어야 비교된다.
   ```bash
   # 예: 이 머지에 들어와도 되는 경로가 docs/ 아래뿐일 때
   A={{REF}}{{MAIN_BRANCH}}; B={{REF}}<브랜치>
   test -z "$(git -c core.quotePath=false diff --name-only "$A...$B" | grep -v '^docs/')" \
     || { echo "범위 밖 변경:"; git -c core.quotePath=false diff --name-only "$A...$B" | grep -v '^docs/'; false; } \
     && git merge --no-ff "$B" -m "[G] Merge <브랜치> → {{MAIN_BRANCH}}"
   ```
3. **build → 전체 시험 → 체계 스모크(L-03).** 스모크는 모듈 사이 실제 값으로 핵심 흐름 하나가 끝까지 도는지 본다(여러 인스턴스·서비스를 실제로 띄워 첫 단계부터 마지막 단계까지). **시험 전용 덧씌움 없이 기본 설정**으로 돈다. 몇 분 안에 끝나게 짠다. 배포 대상의 자원 한도가 개발 기계와 다르면 그 한도로도 한 번 돈다(개발 기계에서만 돌려 배포 환경의 막힘을 놓친 사례). HEAVY·`slot.sh` 규칙을 따른다.
4. **유효 회차만 증거로 쓴다(L-11).** 부하에 민감한 관문(시뮬 등)은 시작 전에 부하(load, 다른 무거운 작업)를 확인하고, 회차마다 실시간 비율·부하를 증적에 기록한다. 프로젝트 기준(예: 실시간 비율 ≥ 0.8) 미만이면 **PASS라도 무효 회차**다. 계속 미달이면 원인을 따로 마스터에 보고한다.
5. **FAIL을 부하 탓으로 넘기기 전에(L-05)** 실패 대상의 하류 상태까지 로그로 본다. 관문 도구는 다음 단계의 전제 상태(준비 보고·기준값 확정·헬스)를 기다리고, 시간 상한을 넘으면 빠진 전제를 적고 FAIL하며, FAIL 로그를 보존해야 한다. 아니면 관문 도구 결함으로 보고 인프라 작업(F-xx)으로 고친다.
6. **결과를 남긴다.** 관문 증적에 실행 HEAD(`git rev-parse HEAD`), build 결과, 시험 수·실패 수, 스모크 판정, 회차 유효성을 적는다. 관문 시작과 끝의 HEAD·`git status --porcelain`이 다르면 그 회차는 버린다.
7. **관문 뒤 미추적 증적을 확인한다(L-11).** `git status --porcelain --untracked-files=all docs/06_evidence/`를 보고 이번 후보의 증적만 커밋한다. 나머지는 내용을 확인한 뒤 지운다.
8. 모두 통과하면 반영한다. 원격 push 정책은 `MANAGER.md` 3장 '원격 push'를 따른다. 하위 브랜치 전파는 `orchestration/tools/sync_main.sh --all`.
